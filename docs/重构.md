• # 推荐方案：以 Run 为核心的模块化单体

当前开发阶段允许破坏性修改，我建议不再修补现有“Session 即任务、Redis Stream 即任务状态”的模型，而是建立清晰的四层概念：

- Session：一段长期对话的容器。
- Run：一次用户请求触发的 Agent 执行。
- Plan：某个 Run 的可版本化执行计划。
- Task：执行 Run 的基础设施作业，不属于领域模型。

这能从根本上解决当前配置漂移、停止即完成、状态混杂、内存状态无法恢复和 Redis/数据库双写不一致的问题。

## 一、总体架构

采用“模块化单体 + Ports/Adapters”，保留一个 Go 服务，暂不拆微服务。

flowchart LR
HTTP["HTTP / SSE"] --> APP["Application Use Cases"]
WORKER["Run Worker"] --> APP

      APP --> DOMAIN["Domain<br/>Session / Run / Plan"]
      APP --> ENGINE["Agent Engine<br/>Planner / Executor / Summarizer"]

      ENGINE --> LLM["LLM Port"]
      ENGINE --> TOOLS["Tool Ports"]
      APP --> STORE["Store Ports"]
      APP --> EVENTS["Event Port"]
      WORKER --> QUEUE["Run Queue Port"]

      STORE --> PG["PostgreSQL Adapter"]
      EVENTS --> PG
      EVENTS --> REDIS["Redis Notification"]
      QUEUE --> REDIS
      LLM --> PROVIDER["OpenAI / Anthropic"]
      TOOLS --> EXT["Search / Sandbox / MCP / A2A"]

核心原则：

1. PostgreSQL 是 Run 状态和业务事件的唯一事实来源。
2. Redis 只负责任务通知、工作队列和实时推送加速。
3. Agent Engine 不依赖 HTTP、Redis、PostgreSQL 或具体 Provider。
4. 所有状态迁移必须经过领域方法，禁止业务代码直接赋值。
5. 配置更新影响后续 Run；运行中的 Run 使用启动时冻结的配置快照。

## 二、领域模型

### Session

Session 只表示对话，不再保存运行状态。

type Session struct {
ID                 SessionID
Title              string
LatestMessage      string
LatestMessageAt    *time.Time
UnreadMessageCount int
CreatedAt          time.Time
UpdatedAt          time.Time
DeletedAt          *time.Time
}

删除当前 Session.Status。前端需要展示的运行状态由最新 Run 投影得到：

{
"id": "session-id",
"title": "会话标题",
"active_run": {
"id": "run-id",
"status": "waiting_input"
}
}

同一 Session 同一时间最多存在一个非终态 Run，通过数据库部分唯一索引保证。

### Run

type RunStatus string

const (
RunStatusQueued       RunStatus = "queued"
RunStatusRunning      RunStatus = "running"
RunStatusWaitingInput RunStatus = "waiting_input"
RunStatusSucceeded    RunStatus = "succeeded"
RunStatusFailed       RunStatus = "failed"
RunStatusCancelled    RunStatus = "cancelled"
)

合法迁移：

stateDiagram-v2

queued --> cancelled

waiting_input --> running
waiting_input --> cancelled

终态禁止继续迁移。用户取消后，即使后台 LLM 稍后返回，也不能把 Run 改回 succeeded。

func (r *Run) WaitForInput(question string, now time.Time) error
func (r *Run) Resume(now time.Time) error
func (r *Run) Succeed(now time.Time) error
func (r *Run) Fail(failure Failure, now time.Time) error
func (r *Run) Cancel(reason string, now time.Time) error

### Plan 和 Step

不再复用一个宽泛的 ExecutionStatus。各聚合使用自己的状态：

type PlanStatus string
const (
PlanStatusDraft      PlanStatus = "draft"
PlanStatusActive     PlanStatus = "active"
PlanStatusSucceeded  PlanStatus = "succeeded"
PlanStatusFailed     PlanStatus = "failed"
PlanStatusSuperseded PlanStatus = "superseded"
PlanStatusCancelled  PlanStatus = "cancelled"
)

type StepStatus string
const (
StepStatusPending   StepStatus = "pending"
StepStatusRunning   StepStatus = "running"
StepStatusSucceeded StepStatus = "succeeded"
StepStatusFailed    StepStatus = "failed"
StepStatusSkipped   StepStatus = "skipped"
StepStatusCancelled StepStatus = "cancelled"
)

重新规划时不修改旧计划，而是：

1. 将旧 Plan 标记为 superseded。
2. 创建新的 Plan Version。
3. 保留旧步骤、失败原因和工具调用审计记录。
4. Run 最终状态只根据当前有效 Plan 决定。

这样不会出现“旧步骤 failed，但新计划成功后 Run 仍被判失败”的问题。

## 三、Agent Engine

当前 PlannerReActFlow.Invoke 已经拆分，无需再次机械拆方法。下一步应改变组件契约。

type Planner interface {
CreatePlan(ctx context.Context, input PlanningInput) (PlanDraft, error)
RevisePlan(ctx context.Context, input RevisionInput) (PlanDraft, error)
}

type StepExecutor interface {
Execute(ctx context.Context, input StepInput) (StepOutcome, error)
}

type Summarizer interface {
Summarize(ctx context.Context, input SummaryInput) (Summary, error)
}

执行结果使用显式联合类型，不再用 ErrWaitForUser 表达正常业务分支：

type StepOutcomeKind string

const (
StepSucceeded StepOutcomeKind = "succeeded"
StepFailed    StepOutcomeKind = "failed"
StepWaiting   StepOutcomeKind = "waiting_input"
)

type StepOutcome struct {
Kind        StepOutcomeKind
Result      string
Failure     *Failure
Question    string
Attachments []Artifact
}

约定：

- StepFailed 是模型或工具返回的业务失败。
- error 表示基础设施、协议解析或系统异常。
- 等待用户输入是正常结果，不使用错误控制流。
- panic 统一映射为 RunFailed，不能写成 completed。
- context 取消时根据数据库状态决定是 cancelled、shutdown interruption 或系统失败。

## 四、上下文与记忆

删除当前没有真正执行容量限制的 SimpleMemory.maxSize，也不再把进程内 Memory 当作事实来源。

新增 ContextBuilder：

type ContextPolicy struct {
MaxInputTokens      int
ReservedOutputTokens int
RecentMessageCount  int
}

type ContextBuilder interface {
Build(ctx context.Context, runID RunID, policy ContextPolicy) ([]llm.Message, error)
}

上下文来源：

- Session 历史消息
- 当前 Run 的计划
- 已完成步骤结果
- Tool call/result 配对
- 附件摘要
- 已持久化的历史摘要

压缩策略：

1. 始终保留 system prompt、当前用户请求和最近消息。
2. Tool call 与 tool result 必须成对保留或成对删除。
3. 超出 token 预算时，先删除较旧的工具细节。
4. 仍超限时生成持久化摘要。
5. 使用模型画像中的 context window 计算预算。

删除以下模糊配置：

- MaxMemorySize
- CompactThreshold
- 固定 keepCount := 10
- 当前空操作 LoadMemory

## 五、配置设计

配置分为三类。

### 部署配置

保存在环境变量或 YAML：

- PostgreSQL、Redis、OSS
- API Key 和其他密钥
- 外部服务地址
- HTTP timeout
- Worker concurrency
- 数据保留周期
- 服务关闭时间

这些配置不通过业务 API 修改。

### 动态运行配置

保存在 PostgreSQL，并由 SettingsManager 管理：

type AgentSettings struct {
MaxIterations    int
MaxRetries       int
MaxPlanSteps     int
MaxSearchResults int
}

规则：

- 启动时读取数据库配置。
- 数据库没有记录时返回完整默认值，而不是空结构。
- 更新时先校验、再持久化、最后原子替换内存快照。
- 每个 Run 保存 settings_revision。
- 配置更新只影响新 Run。
- MaxPlanSteps 必须在 Planner 输出解析后真正校验。
- MaxSearchResults 通过 SearchRequest.Limit 传入适配器。

type SearchRequest struct {
Query     string
DateRange *DateRange
Limit     int
}

这样可以删除当前 Tavily 和 Bocha 中硬编码的 10。

建议范围：

### Prompt 配置

Prompt 不放入通用配置表，也不作为散落在 Go 文件中的超长常量。

推荐：

## 七、事件契约

持久化语义事件：

- run.queued
- run.started
- plan.created
- plan.revised
- step.started
- step.succeeded
- step.failed
- run.waiting_input
- run.resumed
- message.completed
- run.succeeded
- run.failed
- run.cancelled

Token delta 属于实时展示数据：

- message.delta 通过 Redis Pub/Sub 推送。
- 不逐 token 写数据库。
- 断线后客户端读取最后一个 message.completed 恢复。
- SSE id 只用于持久化语义事件，避免一个游标跨 Redis 和 PostgreSQL 两套存储。

domain 中的事件不再提供 ToJSON()，也不依赖 logger。JSON 编解码在 HTTP/PostgreSQL adapter 中完成，序列化失败向上传递错误。

## 八、任务执行与多实例

删除“每个 Session 一个长期 RedisStreamTask”的设计。

改成：

1. 创建 Run 并写入 run.queued。
2. Outbox 将 Run ID 投递到 Redis Queue。
3. Worker 原子获取 Run lease。
4. Worker 调用 Agent Engine。
5. Engine 每一步通过 Run Application Service 提交状态和事件。
6. Worker 定期续租。
7. 进程崩溃后，lease 过期的 Run 可重新投递。

本地只保留一个很小的取消注册表：

type RunningHandles interface {
Register(runID RunID, cancel context.CancelFunc)
Cancel(runID RunID) bool
Unregister(runID RunID)
}

它只用于快速取消当前进程内的执行，不承担任务查询、事件保存或业务状态职责。

## 九、API 契约

建议直接替换旧接口：

POST /api/sessions
GET  /api/sessions
GET  /api/sessions/{session_id}

POST /api/sessions/{session_id}/runs
GET  /api/runs/{run_id}
POST /api/runs/{run_id}/input
POST /api/runs/{run_id}/cancel
GET  /api/runs/{run_id}/events

GET  /api/settings/agent
PUT  /api/settings/agent

行为：

- 新请求通过 POST /sessions/{id}/runs 创建 Run。
- 如果 Session 已有非终态 Run，返回 409 active_run_exists。
- 等待用户输入时使用 /runs/{id}/input 恢复原 Run。
- 取消 Run 后状态为 cancelled。
- 创建 Run 支持 Idempotency-Key，防止客户端重试产生重复任务。
- SSE 使用标准 Last-Event-ID，不再把游标同时放请求体和 Header。
